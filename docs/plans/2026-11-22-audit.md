# Audit against the store standard

Status: audit only, 2026-11-22. Nothing in code, schema or data was changed for it.
Basis: `master` at `c2be588`. `TEST_DATABASE_URL=postgresql://localhost/postgres .venv/bin/pytest -q` gives 186 passed, 0 skipped.

## The standard

1. Categories are fixed lists enforced by the database. Any field one would filter, group or join on takes values from a defined list.
2. Free text only for content people read (title, question, answer, note); never used to group or decide.
3. References are real foreign keys, never names or IDs inside text or JSON.
4. Each fact is stored once; derived values are derived.
5. Anything one would query is a column or table. JSON only for raw audit records, each with a documented shape.
6. Everything is used: every column, function, endpoint, script, module and test is read by something or enforces a rule. Otherwise it goes.
7. Stable readable identifiers for anything a person or config refers to.
8. One vocabulary across database, code and docs; nothing left from the old project.
9. Rules live in the database and are tested against a real database.

Rules are cited below as R1 to R9. "Decided" marks a change already agreed before this audit; everything else is proposed.

## Findings that change the picture

These came out of the audit and are not obvious from the design document:

- **The scope boost does not exist in the running pipeline.** `CohereReranker.rerank` (`app/retrieval/reranker.py`) accepts `detected_provider` and ignores it. Only the legacy `Reranker`, which nothing in `app/` uses, applies a scope boost or the authority rank. So `QueryParser`'s detection only reaches `query_logs.detected_filters`, which nothing reads. The design's test "the reranker boost applies for a question naming either scope" tests dead code.
- **The text fingerprint does not cover what it is meant to cover.** `text_sha256` hashes section `content` only (`app/ingestion/fingerprint.py`). Headings go into `title` (`ReductoParser._extract_sections`) and are not hashed. Non-heading blocks shorter than 10 characters are dropped. `Footer` blocks are kept, although they are the usual place for dates and page numbers. In the 11 cached parser outputs (`plans-local/parsed/`, counted inline when this audit was written, no script kept) there are 419 `Footer` blocks, of which 217 are 10 characters or longer and so enter the text and the fingerprint. There are also 205 dropped non-heading blocks under 10 characters. A changed heading, or a changed short value in its own block, therefore makes no new version. A changed footer makes a false one. The normalisation rule is already listed as unproven. This is concrete evidence for that test.
- **`PUT /documents/{id}` breaks the store.** It rewrites a version's title. Every chunk keeps the old title in its `content` prefix, logged answers saw the old title, and `corpus.yaml` is not updated.
- **Test results cannot be traced to the versions they saw.** `EvalRunner` gets `log_id` from `pipeline.run` but does not store it, so `eval_runs.results` has no link to `query_logs` or `query_log_documents`.
- **Which direction is "higher authority" is not defined anywhere.** `national` = 1, `operator` = 2. The prompt says "prefer higher hierarchy priority". The legacy reranker adds `rank × weight`. So today a larger number means more authority, and an operator rule outranks the national one. Nothing states this.
- **`scripts/test_models.py` has a bug.** It reads `d.get("met")`, but the judge returns `present`, so every fact prints as missed. The script also uses the legacy reranker and OpenAI, so it is marked for removal anyway.

## What the design must not take on

To be stated in the README:

- User accounts, sign-in, roles or permissions beyond the one backend role. The API stays local and unauthenticated.
- Performance tuning: index parameters, caching, batching beyond API limits, latency targets.
- A review screen, or delivering flags to a person (mail, chat). Flags are rows to query.
- Fetching pages and detecting changes; finding sources for a new rule-maker (brief).
- Improving answers: prompt tuning, retrieval quality, citation parsing, authority conflict handling (brief; build notes *The bigger system*).
- Storing original files.

## Questions for you

1. **Table name for a version.** Keep `documents` (as in your decisions) and rename the code's "version" words to "document"? Or rename the table to `versions` and keep the code's words? Recommendation: `versions`, because the brief, the design and every function already say version.
2. **"Eval" or "test".** The schema and code say `eval_questions`, `eval_runs`, `EvalRunner`. The brief and your decisions say test questions and test runs. Recommendation: `test_questions`, `test_runs` in the schema and docs; keep the package `eval/` so it is not confused with `tests/`. Or rename everything to one word?
3. **Rank direction.** Does a larger rank mean more authority, so an operator rule (2) wins over the national one (1)? Should `levels` say so explicitly, e.g. `rank` with "higher wins" in its comment and a test?
4. **Watch address on promotion.** Today `promote_version` moves `sources.address` to the promoted version's address. You decided a person sets the watch address. Should a person's promotion of a candidate also set the address and `confirmed_at` in the same call? Should an automatic promotion never touch it?
5. **Listing address.** Keep it (as `watch_listing_address`) although nothing in the repository reads it, because the monitor needs it? Or drop it until a monitor exists?
6. **Scope detection.** It changes no answer today. Remove `QueryParser`, `detected_filters` and the scope boost idea? Or build the boost into the Cohere path, as Slice 2 of the design planned? If it stays, how does a question name a scope: by the scope's `name`, or by a list of terms per scope?
7. **Version label.** "Title as printed" drops the hand-written "(V1.3, gültig ab 21.05.2025)". The baseline shows the label is how the model tells versions apart. Should a version get a separate `version_label` column? It would be readable (R7), and the prompt could show it.
8. **Indexing settings scope.** Besides model, dimensions, chunk size and overlap: should the tokenizer (`cl100k_base`), the size units (words for prose, tokens for tables) and the chunk header format be part of the settings row? Any of them changes the chunks.
9. **Flag identifier.** Should flags get a readable identity number for people ("flag 12"), or is the uuid fine?
10. **`resolved_by`.** Free text with a person's name (R2 would allow it as content, but it is something one groups by), or a small `people` table with keys? A table is not user accounts, but it is close.
11. **Status and load status.** Merge into one `status` (`loading`, `failed`, `held`, `current`, `retired`), or keep two columns? And should a failed routine load raise `check_failed`? The brief says every check that could not complete is flagged, and with no flag on routine loads a failed one would otherwise be visible only by querying.
12. **Chunk prefix.** Each chunk's `content` starts with `[title — section]`. Store the plain text and build the embedding input from the columns? Same embeddings if built identically, but the prompt would no longer show the title twice. That changes what the model sees, so the baseline would be re-run.
13. **Fingerprint coverage.** Include headings? Drop `Footer` blocks? Stop dropping short blocks from the fingerprint, or from the text altogether? Settle this by the EKZ archive test the design already plans, or decide now?
14. **Page limit.** Record `max_pages` on the version (`page_limit`)? Should two loads of the same file with different limits be two versions?
15. **System prompt in the log.** Only the user prompt is logged. Should the answer settings hold a prompt version or a hash, so a logged answer says which instructions it had?
16. **Answer settings.** Your decisions cover indexing settings. Should a second table hold what answers depend on (`retrieval_top_k`, `rerank_top_n`, rerank model, answer model, judge model, prompt version), referenced by logged answers and test runs? It replaces `model_used` and the rest of `config_snapshot`.
17. **`case_type` values.** The brief's seven cases (changed at the same address, repackaging, candidate elsewhere, unreachable, overdue, answer differs between versions, retired version lists answers)? Some of those are store tests, not questions. Which values do you want?
18. **Flag reason.** Free text inside `detail`, or a fixed list (e.g. `unreachable`, `moved`, `parse_failed`, `load_failed`) as a column?
19. **Parser links.** `parsed_output` keeps the parser's `pdf_url` and `studio_link`. Strip them on load, or keep the response untouched as the audit record?
20. **`POST /ingest`.** Remove it now and bring it back as "hold a candidate" later, or change it now?
21. **Prompt wording.** Rewriting the old-project system prompt changes answers. Do it in this cleanup (re-running the baseline), or leave the wording until the "improving answers" work, which the brief puts out of scope?
